# 🛡️ Event-Driven Resilience & Failure Modes Handled

> **Source:** Extracted from `tests/DsgOmnichannel.IntegrationTests` — every row maps directly to an implemented, runnable integration test.

---

## Failure Mode Matrix

| Failure Mode | The Risk | Built-In Mitigation / Pattern | Verified Test Scenario(s) |
| :--- | :--- | :--- | :--- |
| **Dual-Write / Lost Events (API Side)** | If the `Order` row commits but the broker publish fails (e.g., RabbitMQ down), the `OrderPlacedEvent` is silently lost — no allocation ever happens. | **EF Core Transactional Outbox** (`AddEntityFrameworkOutbox` + `UseBusOutbox`): `POST /api/orders` writes `Order` and `OutboxMessage` in one DB transaction. The sweeper delivers later. | `DualWriteTests` → `PostOrder_CommitsOrderAndOutboxMessageInSingleTransaction`: asserts `OutboxMessage` row count > 0 after a successful `201 Created` response. |
| **Dual-Write / Lost Events (Worker Side)** | Consumer sets `Order.Status = Allocated` and calls `SaveChangesAsync`, then crashes before `Publish()` reaches the broker — `StoreInventoryAllocatedEvent` is lost. | **EF Core Consumer Outbox** (`UseEntityFrameworkOutbox`): intercepts `context.Publish()` inside the consumer and stages it atomically inside the same `SaveChangesAsync` transaction. | `DualWriteTests` → `OrderPlacedConsumer_FollowUpPublish_IsOutboxStaged`: asserts `StoreInventoryAllocatedEvent` is published and `Order.Status = Allocated` after consumer execution. |
| **Duplicate Message Processing / Non-Idempotency** | Broker redelivers the same `OrderPlacedEvent` (e.g., after a consumer ack loss or transient fault). Without deduplication, inventory is decremented twice. | **MassTransit EF Core Inbox Pattern** (`UseEntityFrameworkOutbox` on the receive endpoint): records each `MessageId` in `InboxState`; redeliveries with the same `MessageId` are silently skipped before the consumer body executes. | `IdempotencyTests` → `OrderPlacedConsumer_WhenEventDeliveredTwice_InventoryDecrementedOnlyOnce`: publishes the same event twice with an identical `MessageId`; asserts final inventory = `initialQuantity - 1` (5 → 4, not 3). |
| **Distributed Rollback / Compensating Transaction** | When stock is insufficient, the consumer may set `Order.Status = AllocationFailed` but leave a stale `OrderState` row in `dbo.OrderState` — a half-committed, never-terminal saga. | **MassTransit Saga Compensating Flow** + **`SetCompletedWhenFinalized()`**: consumer publishes `AllocationFailedEvent`; saga transitions to `Faulted` and calls `Finalize()`, causing the EF Core saga repository to DELETE the `OrderState` row. | `DistributedRollbackTests` → `OrderPlacedConsumer_WhenInventoryInsufficient_OrderFailedAndSagaFinalized`: seeds `StoreInventory.Quantity = 0`, asserts `Order.Status = AllocationFailed` AND `OrderState` row is `null` after processing. |
| **Split-Transaction / Dual Authority on `Order.Status`** | Pre-fix, the saga's `ThenAsync` opened a second `DbContext` scope to write `Order.Status`, racing with the consumer's own write — two transactions owning the same field, risking overwrites or inconsistency. | **Single-Authority Separation (Slice 2.2 fix)**: consumer exclusively owns `Order.Status` (Transaction A); saga exclusively owns `OrderState` finalization (Transaction B). No cross-authority writes. | `SplitTransactionTests` → `AllocationFailed_OrderStatusAndSagaStateAreConsistent`: asserts `Order.Status = AllocationFailed` (consumer's field) AND `OrderState = null` (saga's finalization), with no cross-transaction coordination. |
| **Transient Dependency Failure / Retry Exhaustion** | A transient SQL Server blip causes `DbUpdateException` during `SaveChangesAsync`. Without a retry policy the message is immediately faulted and routed to DLQ — a recoverable failure becomes permanent. | **Exponential Backoff Retry** (`UseMessageRetry` with `Exponential(3, 1s, 5s, 2s)`) filtering `DbUpdateException`, `TimeoutException`, `HttpRequestException`. Faulted attempt rolls back cleanly; retry attempt re-reads and commits. | `TransientRetryTests` → `OrderPlacedConsumer_WhenTransientDbFaultOccurs_MessageRetriedAndEventuallyProcessed`: uses `FaultyApplicationDbContext` + singleton `FaultInjector(failuresBeforeSuccess: 1)`; asserts `StoreInventoryAllocatedEvent` published, inventory = 4, and `FaultCount = 1`. |
| **Poison Message / Immediate DLQ Routing** | An unrecoverable message (e.g., unreachable DB → `SqlException`) sits in the retry loop consuming all retry slots and blocking healthy messages behind it in the same queue. | **Selective Retry Allow-list** (`r.Handle<T>()` whitelist + `r.Ignore<ArgumentException>()`): `SqlException` is not in the `Handle<>` list, so the middleware skips all retries and immediately publishes `Fault<OrderPlacedEvent>` (DLQ equivalent). | `PoisonMessageTests` → `OrderPlacedConsumer_WhenDomainExceptionThrown_MessageRoutedToDlqWithoutRetry`: connects consumer to an unreachable DB (`Connect Timeout=1`); asserts `Fault<OrderPlacedEvent>` is published immediately. |
| **Queue Starvation by Domain-Failure Messages** | A domain-failure message (e.g., stock = 0 → `AllocationFailed`) could slow processing if it blocks healthy messages that follow it in the same queue. | **Graceful Consumer Return Path**: consumer handles the `AllocationFailed` case by setting `Order.Status` and returning normally (no exception thrown). MassTransit acks and moves to the next message immediately. | `PoisonMessageTests` → `OrderPlacedConsumer_WhenPoisonMessagePresent_HealthyMessagesStillProcessed`: publishes a poison order (stock = 0) then a healthy order (stock = 5) to the same consumer; asserts `StoreInventoryAllocatedEvent` published and healthy inventory decremented to 4. |
| **Never-Terminal Saga Leak (Happy Path)** | A fully completed `OrderPickedUp` flow leaves the `OrderState` row in `dbo.OrderState` indefinitely, causing unbounded table growth (SRS Known Gap #2). | **`SetCompletedWhenFinalized()`** on the `OrderStateMachine`: when the saga reaches the `Finalized` terminal state, the EF Core saga repository issues a `DELETE` for the `OrderState` row. | `SagaLeakTests` → `OrderSaga_WhenOrderPickedUp_SagaInstanceRemovedFromDatabase`: drives the full happy-path (`OrderPlacedEvent` → allocation → `OrderPickedUpEvent`); asserts `OrderState` row is `null` after pickup. |
| **Never-Terminal Saga Leak (Failure Path)** | An `AllocationFailed` terminal event leaves an orphaned `OrderState` row, accumulating indefinitely even though the order is dead (SRS Known Gap #2). | **`Finalize()` on the `AllocationFailed` transition** + **`SetCompletedWhenFinalized()`**: same deletion mechanism as the happy path, applied to the failure terminal state. | `SagaLeakTests` → `OrderSaga_WhenAllocationFailed_SagaInstanceDoesNotAccumulate`: seeds insufficient stock; asserts `OrderState` row is `null` after `AllocationFailedEvent` is consumed. |
| **Concurrent Inventory Over-Allocation (Race Condition)** | Two consumers read `StoreInventory.Quantity = 1` simultaneously, both decrement to 0, both mark their orders `Allocated` — one unit of stock fulfills two orders (negative inventory). SRS Known Gap #3. | **EF Core Optimistic Concurrency Token (`rowversion`)** on `StoreInventory`: the second `SaveChangesAsync` fails with `DbUpdateConcurrencyException` because the `WHERE RowVersion = <original>` clause matches no row. Retry re-reads `Quantity = 0` and routes to `AllocationFailed`. | `ConcurrentAllocationTests` → `TwoConcurrentOrders_WhenOnlyOneUnitInStock_OnlyOneOrderAllocated`: two `ApplicationDbContext` instances read before either commits; asserts final `Quantity = 0` and `allocatedCount = 1`. |

## Patterns Used

- **Testcontainers SQL Server lifecycle** — `ApiFactory` spins up an ephemeral `mcr.microsoft.com/mssql/server:2022-latest` container per test collection, creates the EF Core schema with `EnsureCreatedAsync()`, and tears it down via `IAsyncLifetime.DisposeAsync()`. All tests run against a real SQL Server engine without touching any external environment.

- **xUnit Collection fixture (`[Collection(IntegrationTestCollection.Name)]`)** — all test classes share a single `ApiFactory` instance, guaranteeing the SQL container is started and migrated only once across the entire suite. Test isolation is achieved via unique `Guid` order IDs and unique `STORE-*/PROD-*` keys scoped per test method.

- **MassTransit in-memory bus substitution** — `ApiFactory` surgically removes all MassTransit namespace descriptors and replaces RabbitMQ with `AddMassTransitTestHarness`, eliminating broker infrastructure as a test dependency while preserving the full EF Core Outbox pipeline behavior.

- **`FaultInjector` singleton across DI scope boundaries** — `TransientRetryTests` registers `FaultInjector` as a singleton so the fault counter survives MassTransit's per-retry scope recreation. This is the only reliable pattern for counting injected faults across multiple retry attempts when each attempt runs in a new DI scope.

- **`FaultyApplicationDbContext` test double** — registered as a drop-in replacement for `ApplicationDbContext` so `OrderPlacedEventConsumer` receives it transparently via constructor injection. This exercises the real retry middleware against a simulated transient `DbUpdateException` without mocking the consumer itself.

- **`OrderRequestBuilder` fluent builder** — provides safe default values for order submission payloads, keeping HTTP-level tests (`DualWriteTests`) concise and mutation-safe across test runs without repeating anonymous object literals.
