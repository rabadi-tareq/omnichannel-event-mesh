## Design Gaps

### Gap 1 — OrderStateMachine has no handler for OrderCancelledEvent, leaving saga instances permanently orphaned after cancellation

**Where:** `OrderStateMachine` in `src/DsgOmnichannel.Worker/Sagas/OrderStateMachine.cs`

**Risk:** An order can only be cancelled when its status is "Allocated", meaning the saga is guaranteed to exist in the "Processing" state at the time of cancellation. RabbitMQ delivers `OrderCancelledEvent` to the `order-state` queue, but the state machine has no configured transition for that event in the "Processing" state, so MassTransit silently discards the message. The `dbo.OrderStates` row is never finalized and is never deleted, leaving the saga permanently orphaned.

**Recommendation:** Add `When(OrderCancelled).Finalize()` inside `During(Processing, ...)` and declare `Event<OrderCancelledEvent> OrderCancelled` in `OrderStateMachine`. Register the event correlation by `OrderId` to match the existing pattern.

---

### Gap 2 — OrderCancelledEvent has no history record, leaving the order audit trail incomplete

**Where:** `OrderStatusHistoryConsumer` in `src/DsgOmnichannel.Worker/Consumers/OrderStatusHistoryConsumer.cs`

**Risk:** `OrderStatusHistoryConsumer` implements handlers for `OrderPlacedEvent`, `StoreInventoryAllocatedEvent`, `AllocationFailedEvent`, and `OrderPickedUpEvent`, but not `IConsumer<OrderCancelledEvent>`. No `dbo.OrderStatusHistories` row is ever inserted when an order is cancelled. The audit trail for an order's lifecycle is incomplete — it will show Submitted → Allocated but never Cancelled.

**Recommendation:** Add `IConsumer<OrderCancelledEvent>` to `OrderStatusHistoryConsumer` with a handler that inserts a row into `dbo.OrderStatusHistories` with Status set to "Cancelled".

### Gap 3 — OrderStatusNotificationConsumer in the API has no idempotency guard, allowing duplicate SignalR notifications on message redelivery

**Where:** `OrderStatusNotificationConsumer` in `src/DsgOmnichannel.Api/Consumers/OrderStatusNotificationConsumer.cs`

**Risk:** The API's MassTransit configuration applies `UseBusOutbox` at the bus level for publishing, but does not apply `UseEntityFrameworkOutbox` at the endpoint level for receiving. The consumer therefore has no `InboxState` deduplication. If RabbitMQ redelivers any message (due to a network blip, consumer crash during acknowledgement, or prefetch timeout), the consumer fires duplicate SignalR notifications to all connected clients, producing duplicate and confusing journey events in the UI.

**Recommendation:** In `MassTransitServiceCollectionExtensions` in the API project, add an `AddConfigureEndpointsCallback` that calls `UseEntityFrameworkOutbox<ApplicationDbContext>(context)` on each endpoint, mirroring the Worker pattern.
